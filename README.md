## Abstract

The **Model Context Protocol (MCP)** is rapidly emerging as the dominant
integration layer between LLM agents and external tools, data, and services.
Yet its specification leaves the responsibility for **cross-tenant isolation** to
individual server implementations, with no formal validation contract. This
project asks a single, sharp question: *under realistic multi-tenant workloads,
do today's MCP servers actually keep tenants isolated — and if not, where do
they fail?*

We address this question with four research questions, an attack taxonomy
spanning ten boundary classes, a reproducible harness with paired
*vulnerable* and *hardened* reference servers, and four empirical experiments
quantifying leakage, cache interference, prompt-injection propagation, and
defense coverage. The full statistical analysis, generated figures, and the
manuscript itself live alongside the code so that every reported number is
traceable to a single command.

## Research Questions

| RQ | Question | Manifest |
| --- | --- | --- |
| **RQ-1** | What is the *baseline cross-tenant leak rate* on a representative vulnerable MCP server, and across which boundary classes? | `experiments/manifests/rq1_baseline.yaml` |
| **RQ-2** | How does the **shared cache boundary** amplify information leakage under concurrent traffic? | `experiments/manifests/rq2_cache.yaml` |
| **RQ-3** | How do **prompt-injection payloads** propagate across tool, resource, and memory boundaries inside a single MCP session? | `experiments/manifests/rq3_injection.yaml` |
| **RQ-4** | Which **defense combinations** (auth, namespace, sandbox, cache-isolation) most effectively close the leakage surface, and at what latency cost? | `experiments/manifests/rq4_defense_combo.yaml` |

See [`docs/05_Experiment_Design.md`](docs/05_Experiment_Design.md) for the
full experimental protocol and [`analysis/SUMMARY.md`](analysis/SUMMARY.md)
for the headline findings.

## Quickstart

Requires **Python 3.11+** and `make`.

```bash
git clone https://github.com/mahiiabdullah/Cross-Tenant-Isolation-Validation-in-MCP-Servers.git
cd Cross-Tenant-Isolation-Validation-in-MCP-Servers
python -m venv .venv && source .venv/bin/activate       # Windows: .venv\Scripts\activate
pip install -r requirements.txt -r requirements-dev.txt
```

### Validate a manifest

```bash
python framework/cli.py validate experiments/manifests/demo.yaml
# → validate: OK (2 tenants, 3 attacks)
```

### Run the end-to-end demo

```bash
make run-demo
# writes analysis/runs/demo/{events.jsonl, report.md, report.html}
```

### Reproduce the four research questions

```bash
python framework/cli.py run experiments/manifests/rq1_baseline.yaml         --output analysis/runs/rq1
python framework/cli.py run experiments/manifests/rq2_cache.yaml           --output analysis/runs/rq2
python framework/cli.py run experiments/manifests/rq3_injection.yaml       --output analysis/runs/rq3
python framework/cli.py run experiments/manifests/rq4_defense_combo.yaml   --output analysis/runs/rq4
```

### Build the paper assets

```bash
python paper/build_paper_assets.py --runs analysis/runs --out paper/figures
```

### Test, lint, type-check

```bash
make test        # pytest tests/ -q
make lint        # ruff check framework attacks mcp_servers tests
make typecheck   # mypy framework attacks mcp_servers
```

## Threat-Model Summary

We model a *multi-tenant MCP deployment* in which a single MCP server (or a
small cluster) hosts several **logical tenants** — distinct organizations or
users — whose agents invoke tools, read resources, and share a connection pool
and (in some configurations) a response cache. The attacker is a **malicious
or compromised tenant** whose goal is to observe, influence, or exfiltrate
state belonging to another tenant.

Boundaries studied: **transport, session, namespace, tool, resource, memory,
cache, auth, prompt-injection, and fuzzing**. The full enumeration lives in
[`docs/04_Attack_Taxonomy.md`](docs/04_Attack_Taxonomy.md).
